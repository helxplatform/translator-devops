# Jaeger v2 Helm Chart Deployment

This folder is a self-contained [Helm](https://helm.sh/) **umbrella chart** that deploys
[Jaeger v2](https://www.jaegertracing.io/) (all-in-one) together with an Elasticsearch
backend for persistent distributed-trace storage in a Kubernetes cluster.

It wraps two upstream charts as pinned, vendored dependencies (see `Chart.yaml` /
`Chart.lock`), so a single `helm install` brings up the whole stack.

## Overview

- **Jaeger chart version**: `4.8.0` (app version `2.18.0`)
- **Elasticsearch chart version**: `8.5.1`
- **Storage backend**: Elasticsearch (persistent single-node for now, but can be enhanced with more shards/nodes for scalability as needed)
- **Architecture**: All-in-one (Collector + Query + UI in a single pod)
- **Trace ingestion**: OTLP gRPC (port 4317) and OTLP HTTP (port 4318)
- **UI access**: Via NGINX ingress with TLS (cert-manager + Let's Encrypt)

> Migrating a client from a Jaeger v1 backend? See [`MIGRATION.md`](./MIGRATION.md).

## Chart layout

| Path | Purpose |
|---|---|
| `Chart.yaml` | Umbrella chart metadata; declares the `jaeger` and `elasticsearch` dependencies and their pinned versions |
| `Chart.lock` | Resolved dependency lock (generated by `helm dependency update`) |
| `charts/*.tgz` | Vendored dependency archives (`jaeger-4.8.0.tgz`, `elasticsearch-8.5.1.tgz`) — committed so installs are reproducible and offline-capable |
| `values.yaml` | Base values for both subcharts (`jaeger:` and `elasticsearch:` blocks); ingress is disabled here and enabled per-environment |
| `renci-dev-values-populated.yaml` | RENCI **dev** overlay — ingress host `translator-otel-dev.apps.renci.org` |
| `renci-robokop-values-populated.yaml` | RENCI **ROBOKOP** overlay — ingress host `robokop-otel.apps.renci.org` |
| `templates/` | Umbrella-level templates/helpers |

Because the dependency archives are committed under `charts/`, you do **not** need to run
`helm dependency build`/`update` or add the upstream Helm repos to install — `helm
install` reads the vendored archives directly. (You only re-run `helm dependency update`
when bumping a dependency version in `Chart.yaml`; see [Updating dependencies](#updating-dependencies).)

## Prerequisites

- Kubernetes cluster with `kubectl` and `helm` configured
- NGINX ingress controller deployed in the cluster
- `cert-manager` deployed with a `letsencrypt` ClusterIssuer
- A `StorageClass` available for PVC provisioning (`basic` storage class is used for the Elasticsearch PVC)

## Deployment

### Step 1 — Pick (or create) an environment overlay

`values.yaml` holds the common configuration with **ingress disabled**. Each environment
enables ingress and sets its host/TLS in a populated overlay applied on top with `-f`:

- `renci-dev-values-populated.yaml` — RENCI dev (`translator-otel-dev.apps.renci.org`)
- `renci-robokop-values-populated.yaml` — RENCI ROBOKOP (`robokop-otel.apps.renci.org`)

To add a new environment, copy one of these and change `fullnameOverride`, the ingress
`hosts`, and the matching `tls` `hosts`/`secretName` (the TLS secret name typically
matches the hostname, e.g. `jaeger.apps.your-org.com-tls` for `jaeger.apps.your-org.com`).

Other settings you may tune in `values.yaml`:

- **Index retention** — a CronJob (`jaeger-es-index-cleaner`) runs nightly at 23:55 and
  deletes Elasticsearch indices older than 21 days. Adjust `jaeger.esIndexCleaner.numberOfDays`.
- **Elasticsearch sizing/storage** — `elasticsearch.replicas`, `elasticsearch.resources`,
  `elasticsearch.volumeClaimTemplate` (StorageClass + size).

### Step 2 — Install

```bash
# RENCI dev
helm install jaeger . \
  -n <your-namespace> \
  --create-namespace \
  -f values.yaml \
  -f renci-dev-values-populated.yaml
```

Swap in `-f renci-robokop-values-populated.yaml` for the ROBOKOP environment.

This deploys Elasticsearch and Jaeger together. The Jaeger pod may restart a few times
until Elasticsearch finishes coming up — that is expected on a cold start.

> **Elasticsearch security:** ES runs with X-Pack security enabled — TLS on the HTTP
> layer (a self-signed cert the chart auto-generates; nothing to manage) plus
> password auth for the built-in `elastic` user. The password ships with a default in
> `values.yaml`; **change it for any real deployment** — see
> [Elasticsearch credentials](#elasticsearch-credentials) below.


## Updating dependencies

To bump the pinned Jaeger or Elasticsearch chart version, edit the `version` in
`Chart.yaml`, then regenerate the lock file and re-vendor the archives:

```bash
helm repo add jaegertracing https://jaegertracing.github.io/helm-charts
helm repo add elastic https://helm.elastic.co
helm repo update
helm dependency update .
```

Commit the resulting `Chart.lock` change and the updated `charts/*.tgz`.

## Elasticsearch credentials

ES runs with security enabled. The password for the built-in `elastic` user is defined
**once** in `values.yaml` under `esCredentials.password` and threaded via YAML anchors
to all three consumers: the ES `elasticsearch-master-credentials` secret, the Jaeger
collector storage backend, and the ES maintenance CronJobs.

The committed default (`changeme-please-override`) is for local/dev convenience only —
**change it before any shared or production deployment.**

To rotate it permanently, edit `esCredentials.password` in `values.yaml`; the anchors
propagate the new value everywhere.

Because `-f`/`--set` overlays do **not** follow YAML anchors, overriding at install time
means setting the three real paths explicitly:

```bash
helm install jaeger . -n <your-namespace> -f values.yaml \
  --set elasticsearch.secret.password='<new-password>' \
  --set jaeger.storage.elasticsearch.password='<new-password>' \
  --set jaeger.userconfig.extensions.jaeger_storage.backends.some_storage.elasticsearch.auth.basic.password='<new-password>'
```

(Or keep them together in a local, gitignored overlay file passed with `-f`.)

## Instrumenting Applications

Jaeger v2 receives traces via the OpenTelemetry Protocol (OTLP). Instrument your apps using the OpenTelemetry SDK and point your OTLP exporter to `http://<jaeger-svc>:4317` (gRPC) or `:4318` (HTTP) if your apps and the jaeger service are deployed in the same namespace.

For apps in a different namespace, use the full service DNS name such as `http://jaeger.<jaeger-namespace>.svc.cluster.local:4317` or just `http://jaeger.<jaeger-namespace>`. However, cross-namespace traffic may be subject to NetworkPolicy restrictions in the k8s cluster. If a NetworkPolicy exists on the jaeger namespace restricting ingress access from other namespaces, you'd need to add a rule allowing traffic from the app's namespace on port 4317 or 4318.

## Future Scalability Considerations

The current deployment is a single-node all-in-one setup suitable for small to medium workloads. The following changes should be considered as trace volume grows:

### Elasticsearch scaling

- **Increase ES replicas**: Change `elasticsearch.replicas` from `1` to 3+ and update `minimumMasterNodes` accordingly. Update the `replicas: 0` Jaeger index settings to `replicas: 1` to enable shard replication.
- **Increase shard count**: Update `shards: 1` to a higher value (e.g. 3-5) in the
  `jaeger.userconfig.extensions.jaeger_storage.backends.some_storage.elasticsearch.indices` block to distribute index load across ES nodes.
- **Enable index rollover**: Replace date-based index rotation with ILM (Index Lifecycle Management) rollover policies for better control over index size. Jaeger supports `esRollover` via a separate CronJob — enable with `jaeger.esRollover.enabled: true`.
- **Dedicated ES nodes**: Separate master, data, and coordinating ES nodes for large deployments using the Elastic Helm chart's `master`, `data`, and `coordinating` node group settings.

### Jaeger scaling

- **Separate Collector and Query**: For high trace volume, split the all-in-one deployment into separate Jaeger Collector and Jaeger Query deployments. The Collector can then be horizontally scaled (`replicas: N`) independently of the Query/UI component.
- **Increase batch processor settings**: Tune `processors.batch.send_batch_size` and `processors.batch.timeout` in `jaeger.userconfig` to optimize throughput vs. latency.

### Archive storage

Jaeger supports a secondary long-term archive storage backend for traces you want to retain beyond the primary retention window. To enable:

1. Add a second ES backend (`archive_store`) to `jaeger.userconfig.extensions.jaeger_storage.backends` pointing to a separate ES index prefix or cluster.
2. Enable archive in `jaeger_query`:
   ```yaml
   jaeger_query:
     storage:
       traces: some_storage
       traces_archive: archive_store
   ```
3. Users can then click "Archive Trace" in the Jaeger UI on any individual trace to preserve it permanently beyond the 21-day cleanup window.

### Authentication for Jaeger UI

Jaeger UI has no built-in authentication. For production deployments with broader access, add authentication at the ingress layer:

- **Basic auth**: via NGINX ingress `auth-type: basic` annotation
- **OAuth2/SSO**: Deploy an [OAuth2 Proxy](https://oauth2-proxy.github.io/oauth2-proxy/) sidecar in front of Jaeger and configure your org's SSO provider
